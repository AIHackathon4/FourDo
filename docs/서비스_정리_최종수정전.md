# FourDo(PODO) 서비스 정리 — 최종 대규모 수정 전 (2026-11-16)

이 문서는 서비스 완성 전 마지막 대규모 수정의 출발점이다. 핵심 가치, 확정된 기능 결정, 지금 구현된 것과 빈틈을 한곳에 모았다.
11/16에 이 문서를 기준으로 최종 수정을 했고, 5장과 7장에 그 결과를 적었다.
설계 상세는 `docs/백엔드_설계_v3.md`, 보고서 원문은 노션 "PODO 최종 보고서"(1장~2.2 작성됨)가 기준이다.

## 1. 핵심 가치

**문제.** 공모전·대외활동·인턴십에 관심은 있지만 "역량·시간이 부족하다"는 판단으로 지원하지 않는 학부생이 많다.
공고는 제출물과 마감만 알려 주고, 내 역량과 시간으로 무엇을 어떻게 어디까지 하면 되는지는 알려 주지 않는다.
판단할 근거가 없으니 학생은 포기를 고른다.

**가치.** 막연한 포기를 근거 있는 판단으로 바꾼다. 공고 하나와 내 프로필을 넣으면 다음 세 가지를 알 수 있다.
1. 내가 할 수 있는 방법이 무엇인지 (제출물마다 내 역량으로 가능한 방법)
2. 내 시간으로 어디까지 가능한지 (실제로 쓸 수 있는 시간과 필요한 시간)
3. 오늘 무엇을 하면 되는지 (하루 단위 실행 계획)

**차별점 (기존 대안 대비).**
- 정보 플랫폼(링커리어·위비티)은 공고를 찾는 데서 끝난다. PODO는 그 공고를 내가 어떻게 준비할지를 맡는다.
- 생성형 AI는 계획을 통째로 만들어서 제약(시험 기간, 못 다루는 도구)을 놓치고 답이 매번 달라진다.
  PODO에서 AI는 공고를 읽고 선택지를 정리하는 데까지만 쓰고, 고르기·시간 계산·일정 배치는 코드가 한다.
- 선배·커뮤니티 조언은 사람이 있어야 한다. PODO는 공고를 본 시점에 바로 쓸 수 있다.

**원칙.** LLM은 선택지를 만들고, 코드가 고른다 (교수님 피드백: 개인화 하나로 차별화, LLM은 추출만).

## 2. 대상과 범위

- 서비스 범위: 공모전, 대외활동, 인턴십
- MVP: AI·SW·데이터 분야 공모전 × 서울 4개 대학(서강대, 이화여대, 서울과기대, 고려대) 학부생
- 디자인(프론트 화면 구성·스타일)은 김유진 님 작업을 유지한다. 기능만 고친다.

## 3. 확정된 기능 결정

| 영역 | 결정 | 구현 상태 |
|---|---|---|
| 입력 | 공고(링크·본문), 학년·전공, 학교, 지역, 신분, 나이, 주당 시간, 바쁜 일정, 시간표 이미지(선택), 역량 7개×수준, 경험, 팀(+팀원 역량), 목표 | 구현됨 |
| 목표 | 완주 / 완성 / 수상 도전 3개 (기본 완성) | 구현됨 (11/16) |
| 참여 가능 여부 | 참여 가능 / 준비하면 가능 / 확인 필요 / 어려움 + 이유. 프로필로 못 보는 자격은 질문 → 답하면 재판정 | 구현됨 |
| 방법 수준 | 최소/표준/차별화 대신 완주형 / 완성형 / 수상 도전형으로 표시 (카드 내부 값은 그대로) | 구현됨 (11/16) |
| 방법 고르기 | 제출물마다 방법 1개를 정해 이유와 함께 보여 준다. 학생이 바꾸는 기능은 11/16에 뺐다(선택이 오히려 불편) | 구현됨 |
| 역량 부족 | 목표 단계 방법을 못 하면 할 수 있는 대체 방법을 제시하고 그렇다고 밝힌다. 학습 자료·팀원 모집 안내는 하지 않는다 | 구현됨 (11/16) |
| 시간 부족 | 아끼는 시간이 큰 제출물부터 한 단계씩 낮춘다 | 구현됨 |
| 실행 계획 | 하루 단위로 본다. 날짜별 배치는 LLM, 제약 검사는 코드. 시간표가 있으면 수업을 피해 시간대 배치. 못 쓰는 날 건너뜀, 마감 전 여유 기간, 제출물별 중간 목표 | 구현됨 (오늘부터 마감일까지) |
| 실행 지원 | 진행 체크 + 다시 짜기만. 캘린더 내보내기, "밀렸을 때 대안"은 넣지 않는다 | 구현됨 ("시간이 모자라면" 카드 제거, 11/16) |
| 개인화 비교 | 같은 카드·같은 엔진으로 개인화 OFF(표준 단계, 프로필 무시) vs ON | 구현됨 |

## 4. 구조

```
공고 링크/본문 ─▶ read_url (페이지 + 첨부 3개까지)
               ─▶ 공고 카드 (LLM 1회, CARD_MODEL, 원문 해시로 캐시 backend/.card_cache/)
                   기본 정보 · 자격 조건(typical 표시) · 평가 기준 · 양식 · 제출물별 방법 선택지 3~5개
                   (단계 tier, 핵심 역량 1~2개와 수준, 만드는 법 how, 작업 단계와 시간)
프로필 ─────────▶ 맞춤 전략 (코드, strategy.choose)
                   역량으로 걸러내기 → 목표 단계로 고르기 → 시간에 맞추기 → 판정
               ─▶ 로드맵 (코드, roadmap.build) 날짜 배치, 진행(progress) 반영
               ─▶ 화면 JSON (backend/adapter.py) ─▶ 프론트 (backend/static/)
시간표 이미지 ──▶ 수업 추출 (Gemini, 선택. 키 없으면 생략) ─▶ 하루별 배치에서 수업 시간 회피
```

| 파일 | 역할 |
|---|---|
| `src/aihack4/card.py` | 공고 읽기, 카드 추출 프롬프트·스키마, 카드 검사(`check_card`) |
| `src/aihack4/strategy.py` | 방법 고르기·판정. 상수: `STRETCH_FACTOR` 1.5, `BUFFER_SHARE` 0.1, `TIGHT_SHARE` 0.85, `TIER_LABEL`, `GOAL_TIER` |
| `src/aihack4/roadmap.py` | 날짜 배치, 주차 묶기 |
| `src/aihack4/feasibility.py` | `Profile`, 자격·팀 비교, 작업일 계산 (예전 엔진 본체도 여기 남아 있음, 평가 스크립트가 사용) |
| `backend/app.py` | Flask: `/api/analyze`, `/api/rejudge`, `/api/replan`, `/api/session/<id>`, `/api/trust`, `/api/health`. 분석 기록은 `backend/.sessions/`에 파일 보관(최대 200개) |
| `backend/adapter.py` | 폼 → 프로필, 엔진 결과 → 화면 JSON, 하루별 시간대 배치 |
| `backend/static/` | 화면 (입력 → 진행 → 결과 → 하루별 할 일 → 전체 일정 → 개인화 비교 → 신뢰도, 내 도전 기록) |
| `tests/unit/` | 230개 통과 (11/16 최종 수정 후) |

모델: 카드 `CARD_MODEL=anthropic/claude-haiku-5.5` (OpenRouter). 시간표는 `GEMINI_API_KEY`가 있으면 Gemini, 없으면 카드 모델의 이미지 입력.

## 5. 빈틈과 알려진 문제 → 최종 수정 결과 (11/16)

**고친 것**

| 문제 | 고친 내용 |
|---|---|
| 개인화의 폭이 카드 선택지에 달려 있고, 디자인 강점 학생에게 맞는 방법이 없었다 | 카드 프롬프트: 완성형·수상 도전형에 강점별(개발·데이터·AI / 디자인 / 기획·글쓰기)로 다른 길을 넣게 했다. 같은 공고에서 디자인·개발·글쓰기 강점 학생이 각각 다른 수상 도전형 방법을 추천받는 것을 확인 |
| 프롬프트를 바꿔도 예전 카드가 재사용됐다 | 캐시 키에 프롬프트·스키마 버전(`CARD_VERSION`)을 넣었다. 붙여넣은 본문의 줄바꿈 차이도 맞춘다 |
| 가정 값에 근거가 없다 | 값 자체는 그대로다(README에 정리). 시간표 없을 때 "하루 12시간" 표시는 없앴다 |
| 하루별 할 일이 7일만 보였다 | 오늘부터 마감일까지 하루씩, 한 주씩 넘겨 본다. 중간 목표일·여유 기간·마감일을 날짜에 표시 |
| 로드맵의 하루 시간과 시간표 배치가 따로 놀았다 | 시간표가 있으면 수업을 뺀 빈 시간이 그날 작업 시간의 상한이 된다. 빈 시간 하나에 안 들어가면 나눠 넣는다 |
| 첫날에 할 일이 없는 경우가 있었다 | 고른 속도는 유지하되 앞당겨 배치해 첫 작업일부터 할 일이 있다 |
| 끝낸 일을 체크하고 다시 짜면 같은 날 같은 일이 또 잡혔다 | 체크한 시간은 오늘 쓴 시간으로 보고 오늘 남은 시간에서 뺀다 |
| 마감이 지난 공고에도 오늘 할 일이 잡혔다 | 마감이 지나면 작업일을 만들지 않는다 |
| 방법을 시간 때문에 낮추면 이전 방법의 이유가 남았다 | 낮춘 이유와 새 방법의 설명만 남긴다 |
| 결과 화면이 "이번 주 추천 작업" 중심이었다 | "오늘 할 일"(없으면 다음 작업일)로 바꾸고, 첫 버튼을 하루별 할 일로 했다. 주차별 화면은 전체 일정으로 남겼다 |
| 비교 화면 제목이 "일반 AI 답변"이었고, 양쪽이 방법 이름만 보여 줬다 | "개인화 OFF / ON"으로 바꾸고 방법·시간·일정을 같은 항목으로 보여 준다 |
| 진행 화면이 타이머였다 | AI 단계는 응답이 올 때까지 "진행 중"으로 두고, 응답이 오면 코드 단계를 마저 표시한다 |
| 서버 장애 때 예시 결과로 대체했다 | 예시 데이터를 없애고, 이유를 알린 뒤 입력 화면으로 돌아간다 |
| "내 도전 기록" 비활성 | 분석한 공고 목록에서 다시 열 수 있다(오늘 기준으로 다시 계산) |
| 방법을 바꾸면 이전 방법의 진행 기록이 남았다 | 방법이 바뀐 제출물의 진행 기록은 지운다 |
| 세션이 메모리에만 있었다 | `backend/.sessions/`에 파일로 둔다. 서버를 다시 켜도 이어진다 |
| 시간표는 Gemini 키가 있어야 했다 | 키가 없으면 카드 모델의 이미지 입력으로 읽는다. 못 읽으면 화면에 알린다 |
| 공고에서 온 글자를 그대로 HTML에 넣었다 | 화면에 넣기 전에 이스케이프한다 |
| 화면에 구현 설명(코드 판정, AI 추출, 코드 계산, 계산에 쓴 가정)이 드러나 있었고 문장이 어색했다 | 구현 표시를 화면에서 빼고 문구를 다듬었다. 조사는 받침에 맞춰 붙이고("은(는)" 없음), 시간 숫자는 화면마다 같은 기준(제출물 작업 시간)으로 맞췄다 |
| 코드 배치가 부자연스러웠다(1시간 단계가 쪼개져 띄엄띄엄, 30분 조각) | 날짜별 배치는 LLM이 하고 코드가 제약(못 쓰는 날, 하루 시간, 순서, 누락, 조각)을 검사한다. 어기면 한 번 다시 받고, 그래도 어기면 코드 배치 |

**남은 것**

- 평가 체계가 v3 엔진에 아직 연결되지 않았다. 신뢰도 화면은 모두 "측정 전"이다. 11/12 평가는 예전 엔진 결과다
  (실행 불가 계획을 '가능'으로 제시 — 개인화 없음 44%, LLM 단독 20%, PODO 5%. 시험 기간 배치 52% / 24% / 0%).
- 카드 선택지와 작업 시간은 모델에 따라 흔들린다(같은 원문은 저장한 카드를 쓰므로 한 번 만든 뒤에는 같다).
  영상·발표 강점 학생의 경로는 따로 확인하지 않았다.
- 가정 값(주말 = 평일 2배, 팀원 수준 '가능', 보완 1.5배 등)은 근거 자료가 없다. 화면에는 보여 주지 않고 README에만 적었다.
- 팀이면 하루별 할 일이 팀 전체 기준이다(누가 어느 일을 하는지는 나누지 않는다).
- 배치를 LLM이 하게 되면서 다시 짜기가 몇 초(실측 약 10초) 걸리고, 같은 조건이라도 처음 받을 때마다 배치가 조금씩 다를 수 있다.
  보고서 2.2의 "일정 배치는 코드가 한다", "같은 입력이면 같은 결과" 문장은 고쳐야 한다.

## 6. 지켜야 할 것

- `.env`와 API 키는 커밋하지 않는다. 수집한 공고 원문·DB(`data/contests/`)와 `backend/.card_cache/`도 커밋하지 않는다.
- 합성 데이터는 평가용으로만 쓴다. 사용자 문제의 근거로 쓰지 않는다.
- 디자인은 유지하고 기능만 고친다.
- 푸시는 확인을 받고 한다. 브랜치 `engine-backend`는 아직 푸시하지 않았다.
