# PODO 기획 v2 — 교수님 피드백 반영 (2026-11-11)

## 1. 바뀐 것 한눈에

| 항목 | 이전 | 이후 |
|---|---|---|
| 차별화 | 참여 가능성 분석 + 실행 계획 + 수집 자동화 등 여러 개 | **개인화 입력 하나**로 집중 |
| LLM 역할 | 자격 해석·작업 분해·조언 (계산은 이미 코드) | **컨텍스트 파악·정보 추출만**. 판단·계산은 코드 |
| 공고 수집 | 자동 수집 에이전트 | 라이선스 문제로 보류, **링크 수동 입력** |
| 평가 | 합성 페르소나 6명 + 관계 검사 | **설문 → 파라미터화 → 합성 데이터**, 일부 **사람 검수**로 LLM 정확도(%) 제시 |
| 발표 | 기능 나열 | **스토리텔링** (심사 비중이 기술보다 큼) |

범위는 공모전만 다룹니다. 인턴십은 판정 구조가 달라서 확장 과제로 둡니다.

## 2. 발표 스토리라인

심사 항목은 문제 정의, 근본 원인 해결, AI 모델 설계 적절성, AI 필요성입니다. 각 항목에 아래 장면을 하나씩 대응시켰습니다.

1. **문제 정의**: 학생들은 공모전 정보가 없어서가 아니라, 내 상황에서 할 수 있는지 몰라서 포기합니다.
   - 근거: 비교과 참여 제약 연구(691명)와 설문 결과(4장)
2. **기존 서비스의 한계**: 슥삭과 링커리어는 관심사 필터링까지만 합니다. 내 일정이나 역량은 보지 않습니다.
3. **근본 원인 해결 = 개인화**: 같은 공고라도 학생마다 답이 달라야 합니다.
4. **AI 필요성**: 개인화 입력이 없으면 AI 계획도 엉망이 된다는 것을 아래 비교 실험으로 보여줍니다.
5. **AI 모델 설계 적절성**: LLM에게 계산까지 맡기면 틀립니다. 그래서 LLM은 읽고 이해하는 일만 하고, 계산은 코드가 합니다.
6. **신뢰도**: 어디까지 믿을 수 있는지 수치로 제시하고, 모르는 부분은 모른다고 인정합니다.

### 개인화 비교 실험 (3·4·5번 장면의 근거)

세 조건을 비교했습니다.
- A: 공고만 주고 LLM이 계획을 짭니다 (기존 서비스에 LLM만 붙인 경우).
- B: 프로필도 주고 LLM이 계산·판정·일정을 혼자 합니다.
- C: PODO. LLM은 작업 분해만 하고, 계산·판정·일정은 코드가 합니다.

세 조건의 계획은 모두 같은 채점 코드로, 각 학생의 실제 제약(시험 기간, 요일별 가능 시간, 마감)과 대조했습니다.

공고 10건(실제 6건, 합성 4건) × 합성 페르소나 6명 = 60케이스, 모델은 DeepSeek V4 Flash입니다.

| 지표 | A. 개인화 없음 | B. 개인화 + LLM 단독 | C. PODO |
|---|---|---|---|
| 실행 불가능한 계획을 "가능"으로 제시 | **37%** | 10% | **0%** |
| 시험 기간에 작업 배치 (시험 기간이 있는 학생) | **80%** | 0% | 0% |
| 쓸 수 있는 시간을 넘긴 주가 있음 | 37% | 13% | 13%* |
| (실제 공고만) 실행 불가능한 계획을 "가능"으로 제시 | 25% | 8% | 0% |

\* C에서 시간을 넘긴 계획은 모두 "어려움" 판정으로 경고가 나간 경우입니다. 수치는 자격 판정 구조를 바꾼 뒤(11/11) 다시 실행한 결과입니다.

- **A의 문제**: 공고마다 계획이 하나뿐이라, 6명의 서로 다른 학생이 똑같은 계획을 받습니다. 그래서 개인화가 필요합니다.
- **B의 문제**: 가용 시간 계산이 20% 넘게 틀린 경우가 26%였습니다(첫 실행 18%). 같은 조건을 다시 돌리면 "가능" 오판 비율도 17%에서 10%로 달라질 만큼 흔들립니다. 작업량을 줄여서 계획을 가용 시간에 끼워 맞추는 경향도 있었습니다. 그래서 계산은 코드가 해야 합니다.
- **발표용 장면**: 시험 기간이 있는 학생에게 A는 시험 주간에 쓸 수 있는 시간(2시간)의 약 두 배를 배치합니다. C는 시험 주를 피해서 배치합니다. 이 비교를 주차별 표로 보여줍니다.
  - 결과 파일: `data/results/personalization_*.md`
  - 실행: `uv run python scripts/compare_personalization.py`

**한계 (발표에서 먼저 밝힐 것)**: 작업 소요 시간 추정 자체가 맞는지는 이 실험으로 검증되지 않습니다. 각 조건의 계획을 그 조건이 낸 시간으로 채점했기 때문입니다. 예를 들어 같은 학생, 같은 공고에서 B는 12시간, C는 23시간이 필요하다고 봤는데, 누가 맞는지는 실제 소요 시간 데이터가 있어야 알 수 있습니다. 이 빈칸은 4장의 설문과 사람 검수로 채웁니다.

## 3. LLM과 코드의 역할 분리

| 단계 | 담당 | 현재 상태 |
|---|---|---|
| 공고 링크·파일 → 구조화 (마감, 자격, 팀 조건, 제출물) | LLM (추출) | 완료 |
| 제출물 → 작업 분해와 작업별 필요 역량 | LLM (컨텍스트 파악) | 완료 |
| 작업별 소요 시간 범위 | LLM 추정 → **설문 데이터로 보정 예정** | 보정 전 |
| 참가 자격 판정 | LLM은 공고마다 한 번 조건을 추출하고, **프로필과의 비교는 코드**가 함. 코드가 확인할 수 없는 조건은 예/아니오 질문 | **완료 (11/11)** |
| 가용 시간, 일정 배치, 판정 | 코드 | 완료 |
| 조언 문장 (요약, 이번 주 할 일) | LLM (계산된 결과를 문장으로만 풀어 씀) | 완료 |

참가 자격 판정을 바꾼 근거는 검증 결과였습니다. 판정이 흔들리는 원인 대부분이 LLM의 자격 해석이었고, 무관한 입력을 바꿨을 때 자격 판단이 유지된 비율은 86%였습니다. 바꾼 뒤의 결과는 다음과 같습니다.

| 지표 | 이전 (LLM이 프로필마다 판단) | 이후 (조건 추출 + 코드 비교) |
|---|---|---|
| 같은 입력 3회 반복 시 판정 일치율 | 93% | **97%** |
| 반복 판정이 모두 같은 케이스 | 82% | **90%** |
| 참가 자격 통제 실험 정확도 | 93% (30건) | **100%** (60건) |
| 무관한 입력 변경에 자격 판단 유지 | 86% | **100%** (구조상 보장) |
| 반복 소요 시간 흔들림 (중앙값) | 34% | 26% |

프로필에 없는 조건("평생교육이용권 이용자" 등)은 "해당하시나요?" 질문으로 바뀌었고, 데모에서 답하면 다시 판정합니다.

## 4. 평가 설계: 설문 → 파라미터 → 합성 데이터 → 사람 검수

### 4-1. 설문 (대학생 대상, 응답 5분 이내)

설문의 목적은 세 가지입니다.
1. 합성 페르소나의 분포를 실제 대학생에 맞춥니다.
2. 작업 소요 시간을 보정할 근거를 모읍니다.
3. 문제 정의의 근거를 모읍니다.

| 문항 | 보기 | 쓰임 |
|---|---|---|
| 학년 / 신분 / 전공 계열 / 거주 시·도 | 선택 | 페르소나 기본 속성 |
| 학기 중 평일 하루에 공모전에 쓸 수 있는 시간 | 0, 0.5, 1, 2, 3, 4시간 이상 | `weekday_hours` 분포 |
| 학기 중 주말 하루에 쓸 수 있는 시간 | 위와 같음 | `weekend_hours` 분포 |
| 주당 아르바이트 시간 | 없음, 10시간 미만, 10~20시간, 20시간 이상 | 시간 변수와의 상관 |
| 시험 기간에 공모전 준비를 완전히 쉬는 기간 | 없음, 1주, 2주, 3주 이상 | `blocked` 길이 |
| 보유 역량 13종과 수준 | 없음, 입문, 가능, 능숙 | `skills` 분포 |
| 공모전 참가 경험 | 처음, 참가, 수상 | `experience` |
| 선호 참가 방식 / 팀원 구하기 어려움 | 혼자, 팀, 상관없음 / 1~5 | `team` |
| **최근 참가한 공모전의 제출물 유형** | 사진, 영상, 기획서, 디자인, 개발, 논문, 수기 | 소요 시간 보정 |
| **그 공모전에 실제로 쓴 총 시간 / 준비 기간** | 시간 / 일 | **LLM 시간 추정 정확도 검증** |
| **처음 예상한 시간과 비교하면** | 훨씬 더 걸림, 조금 더 걸림, 비슷함, 덜 걸림 | 계획 오류 경향 |
| 관심 있었지만 포기한 경험과 그 이유 | 시간, 역량, 팀, 마감 놓침, 자격 불확실, 뭐부터 할지 몰라서 (복수 선택) | 문제 정의 근거 |
| 개인화 입력에 쓸 수 있는 시간 | 1분, 3분, 5분, 10분 이상 | 입력 폼 설계 |

### 4-2. 파라미터화와 합성 데이터 생성
- 응답에서 속성별 분포를 뽑습니다. 평일·주말 시간처럼 같이 움직이는 속성은 결합 분포로 다룹니다.
- 이 분포에서 페르소나를 샘플링합니다. 실제 분포에서 뽑는 일반 세트와, 경계 사례를 의도적으로 늘린 스트레스 세트를 **따로 보고**합니다.
- 생성은 규칙 기반 샘플링으로 합니다. LLM으로 만들지 않기 때문에, 평가 대상 LLM과 생성기가 겹치는 순환 문제가 없습니다.
- CUBIG Syntitan은 표 형식의 설문 응답을 늘리는 데 쓸 수 있습니다. 시드가 적으면 편향이 커지므로, 원본 분포와 비교한 수치를 함께 제시합니다.

### 4-3. 사람 검수 (순환 문제 보완)
- 합성 케이스 30건을 뽑습니다. 팀원 2명이 각자 판정(4단계)과 "이 계획이 현실적인가(1~5점)"를 매깁니다.
- 보고할 수치:
  - 사람 사이 일치도 (kappa)
  - 사람과 PODO의 판정 일치율 (%)
  - 사람과 B(LLM 단독)의 판정 일치율 (%)
- 설문에서 실제 소요 시간을 받은 응답은 같은 제출물 유형의 LLM 추정 범위와 비교합니다. 범위 적중률과 평균 오차를 보고합니다.

### 4-4. 지금까지의 자동 검증 (정답 없이 가능한 부분)

| 검사 | 결과 |
|---|---|
| 코드 판정 논리 관계 검사 (264건) | 100% |
| 참가 자격 통제 실험 | 100% (60건), 자격 미달을 "충족"으로 본 오류 0건 |
| 반복 판정 일치율 (자격 구조 전환 후) | 97% |
| 자격 조건 반복 추출 일관성 | 공고 10건 중 9건 (나머지 1건은 해석 차이, 서비스에서는 공고당 한 번만 추출) |

실행: `uv run python scripts/eval_feasibility.py`

## 5. 남은 작업 (우선순위 순)

1. **설문 배포.** 응답을 모으는 데 시간이 걸리므로 가장 먼저 합니다. 위 문항으로 구글폼을 만듭니다.
2. ~~참가 자격 판정 구조 전환~~ (11/11 완료)
3. **데모에 개인화 유무 비교 화면 추가.** 같은 공고를 "프로필 없이"와 "내 프로필로" 나란히 보여줍니다.
4. **사람 검수 시트 생성과 라벨링** (팀원 2명).
5. **설문 응답 → 페르소나 생성기 → 평가 재실행.**
6. **발표 자료**를 2장 스토리라인 순서로 구성합니다.
7. **교수님께 추가 질문 메일.** 사람 검수 표본 크기와 kappa 기준, 설문 응답 수가 적을 때 Syntitan을 어떻게 쓰면 좋을지 여쭙니다.
